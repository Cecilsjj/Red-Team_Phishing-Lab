# Red Team Phishing Simulation Lab

## Project Overview

This project demonstrates the development and execution of a controlled phishing email simulation using Python, Docker, Mailpit, and a locally hosted HTTP server.

The objective was to understand how phishing emails are constructed, how impersonation techniques work, how email messages are delivered, and what security evidence defenders can investigate.

All testing was performed in an authorized local environment using fictional identities. No external recipients were targeted, and no credentials were collected.

## Phishing Simulation Scenario

**Fictional organization:** Northstar Technologies

**Sender:** `security@northstar-support.example`

**Recipient:** `employee@northstar.example`

**Subject:** Action Required: Account Verification

The simulation used a lookalike sender domain and an account-verification pretext to demonstrate common phishing techniques.

The email contained a link to a harmless verification page hosted at `127.0.0.1:8080`.

## Investigation Methodology

### 1. What Happened?

1. Constructed plain-text and HTML phishing simulation templates.
2. Created a local account-verification landing page.
3. Submitted a simulated phishing message through SMTP to Mailpit.

### 2. What Was the Outcome?

1. Mailpit successfully received the simulated email.
2. The local landing page was verified as accessible.
3. The original email was exported in `.eml` format for defensive investigation.

No passwords were collected, and no unauthorized account access was demonstrated.

### 3. Investigate Further?

**Yes.**

The companion Blue Team investigation will examine the email headers, sender identity, suspicious URL, routing metadata, and defensive controls.

## Email Authentication

The project includes synthetic Sender Policy Framework (SPF), DomainKeys Identified Mail (DKIM), and Domain-based Message Authentication, Reporting, and Conformance (DMARC) results.

These results demonstrate that an attacker-controlled lookalike domain could pass email authentication.

**Important:** These values are illustrative training data, not authentication results generated by a production email gateway.

These mappings describe simulated phishing behavior rather than a confirmed real-world compromise.

## Evidence and Deliverables

## Key Lessons Learned

- Email display names do not prove sender authenticity.
- Lookalike domains can create misleading sender identities.
- SPF, DKIM, and DMARC do not guarantee an email is safe.
- SMTP message headers are useful investigation evidence.
- Original `.eml` files preserve important forensic information.
- Local simulations allow phishing behavior to be studied without targeting real users.

## Security and Scope

This project is intended strictly for authorized cybersecurity education.

All email identities use reserved `.example` domains. SMTP delivery and HTTP hosting were restricted to the local testing environment.

The landing page does not collect credentials or authentication tokens.
